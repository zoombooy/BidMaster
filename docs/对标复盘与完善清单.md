# BidMaster 对标复盘与完善清单

> 基准：对 OpenBidKit_Yibiao（易标）、BidPilot-AI、tender-extract 三个项目源码级深挖后，与当前代码（v0.1.x，含实战迭代）逐维度对照。
> 结论先行：**核心抽取链路已达到或超过对标项目**（多分标建模、证据坐标、表格结构化、机械校验、诚实四态均领先），
> 差距集中在**业务字段覆盖广度、清洗校验精细度、评测数据飞轮、废标检查、补遗工作流**五个方面。

## 一、我们已领先的维度（不需要改）

| 维度 | 我们 | 对标项目 |
|------|------|---------|
| 多分标(lot)建模 | 评分项按分标分组、逐分标权重/公式矩阵、分组机械校验 | BidPilot-AI **无分标实体**，多文件拍平抽取互相污染 |
| 证据定位 | 页码+bbox+字符偏移+原文片段 | BidPilot-AI 无坐标、docx 页码恒为 1；tender-extract 五维但我们等价 |
| 表格结构化 | 表格→结构化行（评分表逐行映射） | BidPilot-AI 只计数不解析；tender-extract 转 Markdown 再正则 |

| 分值机械校验 | 按 lot 分组"大类合计==子项合计"，32/33 实测 | 三家都没有系统性合计校验（BidPilot 的 covered 恒为 0 是未完成功能） |
| 扣分项/梯度量化 | （-30分）penalty 识别、"优16-20分"→grades | 均无 |
| 诚实四态+完成门 | found/n.a./not_found/failed + 处理账本完成门 | 易标"没有提及/未提取到"两级（类似但无账本） |

## 二、差距清单（按优先级）

### P0-1 业务字段覆盖不足（对标：易标 18 项 + tender-extract 40 字段）

我们只有 17 个字段。对标后缺失的高价值字段：

| 缺失字段 | 来源 | 价值场景 |
|---------|------|---------|
| 保证金退还条件/不予退还情形 | 易标 marginInfo | 投标决策（钱能不能拿回来） |
| 保证金缴纳方式/截止时间 | 易标 marginInfo | 操作执行 |
| 异议/质疑处理渠道与时限 | 易标 openBid | 维权 |
| 评标委员会组成与职责 | 易标 evaluationBid | 评标博弈 |
| 履约保证金/合同签订流程 | 易标 signingProcess | 中标后动作 |
| 违约/不可抗力/争议解决 | 易标 terminationCondition | 风险评估 |
| 交货与服务的 9 字段（验收/质保/售后/响应时限/培训/文档） | 易标 deliveryAndServiceRequirements | 服务类标书核心 |
| 招标文件获取方式/售价/递交地点 | 易标 keyInfo | 投标准备 |
| **统一社会信用代码** | tender-extract business_license（18 位+校验位） | 资格核验 |
| **法定代表人** | tender-extract legal_representative | 资格核验 |
| **联系电话/邮箱** | tender-extract contact_info | 联系 |
| 付款条件/结算方式 | tender-extract payment_terms | 商务决策 |
| 采购清单/工程量清单摘要 | 易标 procurementList | 报价准备 |

**改法**：扩展 FIELD_CATALOG 与 FIELD_RULES（约 +14 个字段，每个 1-2 条规则包），
必填集合保持 5 个不变。成本约 1 天。

### P0-2 类型化清洗器/校验器 + 类型化合并策略（对标：tender-extract 最强项）

我们的 guard 是粗粒度的（长度/数字窗口）。tender-extract 的精细校验器准确率收益最大：

1. **身份证 GB11643 校验位算法**（权重表+校验码表，不合格直接丢弃）——人员信息核验
2. **公司后缀白名单**（有限公司/集团/局/中心/医院…，拒绝 URL 误命中）——tenderer/agency 守卫
3. **占位词黑名单**（无/暂无/略/详见/见附件——我们部分有，需补全）
4. **金额合理区间**（amount 1~100 亿、deposit 1 千~10 亿，区间外置信度×0.5 而非丢弃）
5. **日期合理窗口**（now-3650 天 ~ now+1825 天——比我们的 2018-2040 更科学）
6. **重复字符占比过滤**（`len(set(v)) < len(v)*0.3` 判无意义值）
7. **FieldMerger 类型化合并**：金额选"第一个能解析且落在合理区间的候选"、日期取窗口内、编号校验格式——而不是无条件取最高置信度
8. **冲突检测规则**：数值最大/最小比 >5 → 标"数值差异过大（可能多分标）"；唯一值 >3 个 → 提示

### P0-3 废标风险四象限解析（对标：易标 discardedBids，用户价值最高的单点）

易标的废标解析是全项目唯一"放开经验补充"的地方，结构化约束极强：

```
# 招标文件中明确提到的        ← 严格溯源，保留关键句
  ## 无效投标
  ## 废标项
# 此类标书还可能涉及的        ← 允许经验补充（高风险遗漏）
  ## 无效投标
  ## 废标项
```
配套纪律：每小节最多 3-5 条（上限抑制幻觉）、同义词归并（否决投标=无效投标=重大偏差）、
检查侧 severity 三级（high/medium/low）+ pending/confirmed 两态。

**我们的现状**：只有 ★实质性条款抽取。②之四前附表的 30 行否决情形表（我们已能解析出表格！）
没有转化为结构化废标清单。**改法**：新增 `rejection.py`——规则层解析"否决情形/废标条款"
表格与 ★条款，LLM 层补"可能涉及"象限（需 Key），输出 `rejection_risks` 报告段。

### P0-4 MCP `local_path` 任意文件读（安全修复）

`analyze_tender(local_path=...)` 可读服务器任意文件（如 /etc/passwd 若可解析）。
**改法**：路径白名单——只允许 `work/` 目录、环境变量 `BIDMASTER_ALLOWED_PATHS` 指定目录，
拒绝 `..` 与符号链接逃逸。

### P1-1 评测数据飞轮（对标：tender-extract 最有价值的基础设施）

tender-extract 的闭环：**低置信/冲突/LLM来源 → 确定性ID复核队列 → 人工裁决(accept/correct/reject)
→ resolved 决策导出为部分标注金标 JSONL → CI --fail-under 门禁**。
部分标注设计（只评标注字段，未标注不计 FP）使金标集可以增量生长。

**我们的现状**：有低置信复核 issue 列表，但无复核存储、无金标回流；金标集只有 1 份样例。
**改法**：① ReviewStore（JSONL+确定性 ID=sha256(doc|field|candidates)）；② `bidmaster review` CLI
（list/resolve/export）；③ export 生成 `evals/golden/*.jsonl`；④ evaluate.py 支持 JSONL 部分标注格式；
⑤ 实战中每修一个错例就回流一条金标。

### P1-2 补遗/澄清版本链 + 事实冲突确认工作流（对标：BidPilot-AI）

- 文档版本实体（正文/补遗/澄清 + document_type + supersedes）
- 补遗到达 → 对 限价/工期/截止/质保 等关键事实做值比对 → 不一致生成**人工确认任务**
  （candidate_value/old/new/risk=high）→ 确认后回写并级联失效受影响抽取
- BidPilot 的教训要避开：它的增量重算是 INSERT 型（产生重复行）；我们的 checkpoint 幂等机制可直接复用

### P1-3 分层置信度模式库（对标：tender-extract patterns.py）

我们每字段 1-2 个模式单一置信度；tender-extract 每字段 4-8 个模式分 5 层
（0.95 精确标注 → 0.90 带语境标签 → 0.85 符号 → 0.80 宽松 → 0.65-0.70 启发式裸值），
外加 0.98/0.99 的针对性修正（PDF 折行项目名）。**改法**：RulePack.patterns 改为
`[(regex, confidence, description)]` 列表，按字段渐进覆盖。

### P1-4 多标段识别与聚焦（对标：易标 bidSectionExtractionTask）

易标流程：行号前缀 → AI 识别标段行范围 → 用户选定标段 → sectionHint 注入全部解析聚焦。
我们的 lot 只是被动提示。**改法**：解析后提供 `list_lots` → 用户/Agent 选定 → 只对该 lot 的
章节范围重跑抽取（checkpoint 已支持定向重跑，缺"范围过滤"参数）。

### P2（二期方向，暂不动手）

- 易标式"18 项 LLM 解析编排"（prompt cache 预热+并发+模板化 JSON）——需 LLM Key；注意其教训：
  项间无交叉校验、11/18 项不进下游（我们按需解析更优）
- 分段解析+AI 合并（超长文档超上下文时）
- 覆盖状态机与 Fixer 分级（写标侧）
- pgvector 业绩匹配层
- 审阅工作台前端（bbox 高亮，我们的证据数据已就绪）

## 三、吸收时要注意的对标项目缺陷（避免照搬）

1. **易标**：18 项中 11 项不进下游流水线（给人看的冗余解析）；代码层零 JSON 校验；
   项间冲突消解全靠合并提示词。→ 我们按需解析+宿主校验的路线更优，只吸收其字段清单与废标纪律。
2. **BidPilot-AI**：Reviewer 4 检查器里 LLM 语义审查路由预留未实现；ScoringItem.coverage 恒为
   uncovered；增量重算重复 INSERT。→ 吸收 ConfirmationTask 工作流形态，不吸收其实现。
3. **tender-extract**：28/40 字段无规则模式（只有 LLM 恢复）；rules.py 与 extraction_engine
   双引擎漂移；切块去重默认关闭。→ 吸收其校验器与评测飞轮，字段按需增补。
